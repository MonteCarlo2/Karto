# Фоновый сбор данных кабинетов: архитектура и план

Статус: план; часть решений принята 22.10.2026 (раздел 0). Код фундамента написан и проверен тестами, миграция в базе не применена.

## 0. Принятые решения (22.10.2026) и что уже сделано

- **Сроки хранения: 180 дней** для истории по дням, событий, закрытых задач, отзывов и вопросов, журнала действий агентов. Журнал прогонов 30 дней. Очистка: функция `seller_hub_prune_all()` (в черновике миграции), воркер вызывает её раз в сутки.
- **Текущее состояние заменяется** (одна актуальная версия), копится только история по дням. Сырые ответы WB, отчёт реализации по строкам, прошлые акции, тексты карточек не храним.
- **Ничего не дублируем**: история по товарам уже в `seller_hub_metric_daily`, отзывы в `seller_hub_feedbacks`, журнал агентов в `seller_hub_agent_actions`. Добавляется только то, чего нет: кабинеты и согласие, расписание источников, журнал прогонов, серверные снимки, реклама по дням (`seller_hub_ad_daily`).
- **Магазин = пара `user_id` + `marketplace_id`**, как во всех таблицах. Отдельный `cabinet_id` откладываем.
- **Читаемость**: понятным языком оформлены только самые ключевые показатели (представление `seller_hub_v_cabinet_health`); остальное устроено под скорость и нужды сервиса.
- **Сначала локально**, потом закрытый раздел только для владельца (список разрешённых аккаунтов), потом одна крупная выкладка на TimeWeb (деплой ~20 минут).
- **Telegram в конец**, раздел «Кабинет и API» с фоном не парный (нужен лишь переключатель согласия).
- Реестр лимитов WB: `src/lib/seller-hub/wb-limits` (из спецификации), шлюз `WbRateGate`. Источники и частоты: `src/lib/seller-hub/sync/sources.ts` (тест проверяет, что фон занимает не больше половины лимита WB при 5 000 товарах), расписание: `sync/schedule.ts`.
- Перед любой записью в кабинет (цена, позже реклама и остатки) читаем актуальное значение и сверяем с тем, что видел человек (сделано для цены).

## 1. Где мы сейчас (факты из кода)

- **Токен WB хранится на сервере**, зашифрованным (`auto_reply_marketplace_secrets`, чтение `openSellerHubWbToken`). Его уже читают маршруты и cron автоответов. Технической преграды, чтобы сервер ходил в WB без открытого интерфейса, нет.
- **Снимок кабинета живёт в браузере** (`localStorage`, ключ `karto-seller-hub-v1:<userId>`): каталог, цены, остатки, заказы FBS, поставки, реклама, акции, финансы, отзывы. Собирается набором вызовов из браузера, часть методов WB догружается позже (воронка, остатки, отчёт реализации).
- **События, задачи и история пересчитываются из браузера**: клиент отправляет показания (`/events/reconcile`, `/tasks/reconcile`). Закрыл вкладку, ничего не происходит.
- **Серверный кэш есть**, но он по пользователю (`seller_hub_data_cache`: `user_id + marketplace_id + cache_key`). Клиент с несколькими кабинетами одного маркетплейса смешает данные.
- **Cron есть только для автоответов** (`/api/cron/auto-reply-*`, секрет `CRON_SECRET`, расписание задаётся снаружи).
- Уже работают без клиента (серверные, идемпотентные): новости WB (`/events/news`, курсор в кэше), история показателей по дням (`/analytics/history`, докачка по 3 дня), запись событий без дублей.

## 2. Цель

Платформа сама следит за кабинетом: свежие данные, события, задачи и (позже) агенты работают без открытого интерфейса, уведомления уходят в Telegram и на почту.

## 3. Модель данных (новые таблицы, только добавление)

| Таблица | Зачем | Ключевые поля |
|---|---|---|
| `seller_hub_cabinets` | кабинет как сущность (сейчас его нет) | `id`, `user_id`, `marketplace_id`, `name`, `status` (ok / token_lost / paused), `consent_at`, `last_ok_at`, `sync_state jsonb` |
| `seller_hub_sync_runs` | журнал прогонов | `cabinet_id`, `source`, `started_at`, `finished_at`, `status`, `error`, `rows` |
| `seller_hub_snapshots` | серверный снимок по источнику | `cabinet_id`, `source`, `payload jsonb`, `version`, `loaded_at` |
| `seller_hub_outbox` | очередь исходящих уведомлений | `cabinet_id`, `event_key`, `channel`, `status`, `attempts`, `sent_at` |

Остальное переиспользуем: `seller_hub_product_events`, `seller_hub_tasks`, `seller_hub_metric_daily`.

**Кабинет в ключах.** Таблицы `seller_hub_*` с ключом `user_id + marketplace_id` переходят на `cabinet_id` (миграция с заполнением по умолчанию, чтобы не потерять данные). Решает риск смешивания кабинетов.

## 4. Расписание и лимиты WB

WB жёстко ограничивает запросы, поэтому сбор это очередь, а не «обновить всё сразу».

| Источник | Лимит (по коду и документации) | Частота сбора |
|---|---|---|
| Каталог, цены, остатки продавца | высокий | 30–60 мин |
| Воронка и отчёт об остатках (analytics-api) | ~1 запрос в 21 с, общий лимит | 1 раз в 2–3 ч |
| Отчёт реализации (finance) | редко | 1 раз в сутки |
| Заказы (Statistics) | 1 запрос в минуту | 1 раз в 1–2 ч |
| Реклама, статистика | ~1 запрос в минуту, окно ≤ 31 дня | 1 раз в 1–2 ч |
| Новости портала | 1 в минуту (обычный токен: 1 в час) | раз в 30 минут |
| Отзывы и вопросы | умеренный | 15–30 мин |

Правила планировщика:
1. Один кабинет один источник за раз (общий лимит токена).
2. Задачи по приоритету: токен и доступы, затем остатки и заказы (критично), затем аналитика, затем история.
3. При 429: пауза по `Retry-After`, увеличивающаяся задержка, источник пропускается до следующего окна; данные не затираются (последний хороший снимок остаётся).
4. Ручное обновление в интерфейсе тоже идёт в очередь, чтобы не бить по лимиту параллельно с фоном.
5. Каждый прогон пишется в `seller_hub_sync_runs`; в интерфейсе виден «возраст данных» и причина, если источник не обновился.

## 5. Конвейер одного прогона

`источники → серверный снимок → производные`:
1. Сбор источников в `seller_hub_snapshots` (серверный аналог того, что сегодня собирает браузер; функции WB-клиента уже серверные).
2. Производные: история по дням, события (те же `diffSellerEvents`, `diffStoreSignals`, `smartEvents`, `newsToEvents`), задачи (`reconcileTasks`).
3. События и задачи пишутся теми же идемпотентными записями, что и сегодня; движки не меняются, меняется только то, кто их запускает.
4. Новые события попадают в `seller_hub_outbox`.

Браузер перестаёт быть источником правды: он читает серверный снимок и показывает возраст данных. Локальный кэш остаётся для скорости.

## 6. Доставка уведомлений

- Пользователь выбирает каналы и что слать (направления и «Обратить внимание», уже есть в «Событиях»).
- Telegram: бот, привязка через одноразовый код (шаблон уже есть у автоответов: `auto_reply_telegram_*`). Почта: существующий почтовый канал.
- Тихие часы, лимит сообщений в сутки, группировка серий (как в ленте) чтобы не спамить.

## 7. Согласие и безопасность (решить)

- Токены уже хранятся; для фонового режима нужно **явное согласие** (`consent_at`), понятная формулировка в подключении кабинета, кнопка «отключить и удалить данные».
- Токен в логи не попадает, права токена проверяются при каждом прогоне; потеря доступа это событие «Система» и пауза кабинета.
- Срок хранения: история 400 дней (есть), снимки перезаписываются, журнал прогонов 30 дней.

## 8. Фазы

| Фаза | Что | Зависит от | Оценка |
|---|---|---|---|
| 0 | Решения: согласие, Telegram-бот, расписание (Vercel cron или внешний) | владелец | — |
| 1 | `cabinet_id` в ключах + `seller_hub_cabinets` + журнал прогонов + проверка здоровья токена | 0 | малая |
| 2 | Фоновые источники без снимка: новости, история по дням, отзывы | 1 | малая (почти готово) |
| 3 | Серверный снимок: каталог, остатки, заказы, реклама, акции, финансы, воронка, реализация | 1 | большая (ядро) |
| 4 | События и задачи по серверному снимку, возраст данных в интерфейсе | 3 | средняя |
| 5 | Outbox и Telegram/почта | 4 | средняя |
| 6 | Агенты на фоне (цены, реклама, ответы) | 3, 5 | большая, отдельный план |

Фазы 1 и 2 можно делать сразу после решения по расписанию, они ничего не ломают. Фаза 3 главная работа и главный риск (лимиты WB, объём, ошибки частичной загрузки).

## 9. Риски и защита

- **Лимиты WB делятся с ручными действиями клиента.** Очередь и ручное обновление через неё.
- **Частичные данные** уже ловятся (мерцание задач закрыто паузой 30 минут); на сервере добавляется проверка полноты прогона: снимок публикуется только целиком, иначе остаётся прежний.
- **Стоимость и время**: cron на серверной платформе с лимитом по времени, прогон делится на короткие шаги с сохранением курсора (как у новостей и истории).
- **Мульти-кабинет**: до фазы 1 не подключать клиентов с несколькими кабинетами одного маркетплейса.

## 11. Запуск (состояние на 22.10.2026)

### Локально (сейчас)

```
npx tsx --env-file=.env.local scripts/seller-hub-worker.ts --enable <userId>   # один раз: включить фон для кабинета (согласие владельца)
npx tsx --env-file=.env.local scripts/seller-hub-worker.ts                     # цикл, проверка каждые 30 с, остановка Ctrl+C
npx tsx --env-file=.env.local scripts/seller-hub-worker.ts --once              # один проход и таблица фактических запросов к WB
npx tsx --env-file=.env.local scripts/seller-hub-worker.ts --status            # состояние источников из представления seller_hub_v_cabinet_health
```

### На сервере (TimeWeb) — когда будете выкладывать

1. Код выкладывается через GitHub, как обычно (около 20 минут). Миграция `20261022_seller_hub_background_sync.sql` уже применена в боевой базе.
2. Переменные окружения на сервере: `CRON_SECRET` (уже есть для Автоотзывов), ключ шифрования токенов и ключи Supabase (уже есть), **`SELLER_HUB_ALLOWED_USER_IDS=<id вашего аккаунта>`**. Без последней переменной на боевом сервере раздел закрыт для всех. Когда раздел будет готов для всех: `SELLER_HUB_PUBLIC=1`.
3. Запуск фона, один из двух способов:
   * **Cron-маршрут (как у Автоотзывов):** внешний cron раз в минуту вызывает `GET /api/cron/seller-hub-sync` с заголовком `Authorization: Bearer <CRON_SECRET>`. Маршрут отвечает сразу, а чтение WB продолжается внутри процесса сервера. Подходит для постоянно запущенного Node-сервера; на serverless-платформе процесс после ответа останавливают, там этот способ не годится.
   * **Отдельный процесс:** `npx tsx scripts/seller-hub-worker.ts` под pm2 или systemd рядом с приложением (перезапуск при падении). Надёжнее, если сервер перезапускается часто.
   Не включайте оба способа одновременно без нужды: безопасно (источник защищён арендой в базе), но лишняя работа.
4. Пока фон включён для кабинета, браузер не читает WB для данных воркера (реализация, воронка, остатки WB, платное хранение, отзывы, статистика рекламы, блокировки): берёт готовый снимок `GET /api/seller-hub/sync/snapshot` и показывает возраст данных. Если данные старше 40 минут, в шапке появляется пометка «Данные от …».
5. Если фон нужно отключить для кабинета: `update seller_hub_cabinets set background_enabled = false where user_id = '<id>'`. Интерфейс вернётся к прежней работе из браузера.

### Что делает каждое действие в интерфейсе

Любой запрос, меняющий кабинет (реклама, цены, остатки, акции, карточки, фото, поставки), после выполнения помечает нужные источники «перечитать сейчас», воркер подхватывает за ≤30 с. Запись цены перед отправкой сверяется с текущей ценой в WB (если её уже поменяли, запись не идёт). Себестоимость хранится у нас, при её изменении задачи и маржа пересчитываются сразу.

### Известные ограничения

* Аренда источника держится до 10 минут: если воркер остановили посреди чтения, этот источник ждёт до конца срока.
* Часть старых клиентов WB делает запросы, которые всегда возвращают 422/400/404 (автоакции не поддерживают список товаров, и т.п.). Они занимают немного лимита и не мешают.
* Telegram и почта не подключены (отложены до конца).

## 12. Источники, добавленные 23.10.2026

Сервер сам читает без открытого интерфейса (`sync/sources.ts`, `sync/jobs.ts`):

| Источник | Что делает | Частота |
|---|---|---|
| `tariffs` | `GET /api/v1/tariffs/box` → снимок тарифов по складам; из него событие «WB повысил/снизил тарифы логистики/хранения» (медиана по складам, порог 1,5%, ≥10 общих складов) | час |
| `news` | новости портала WB → события «Новости» с профилем из базового снимка (категории, бренды, FBS/FBW, склады, акции) и отключёнными рубриками из настроек | 20 мин (до 3 страниц подряд через ~70 с) |
| `history` | воронка законченных дней и остаток на сегодня → `seller_hub_metric_daily` (по 3 дня за прогон, пока не докачано) | 3 часа |

Общий код маршрутов и фона: `news/refresh.ts`, `history/refresh.ts`. Вкладки в режиме `background` не обращаются к WB за этим сами: новости не запрашиваются, история читается `readOnly`, блокировки и воронка/реализация берутся из снимка, статистика рекламы за 7 дней и 7 дней до них берётся из снимка. Оставшиеся запросы к WB из браузера: выбранные пользователем периоды и детализация (период аналитики, рекламные кластеры и ставки, регионы, поставки, склады, поисковые запросы, приёмка).
